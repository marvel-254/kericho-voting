Terms of Use

Last updated: 28 September 2026 — Kericho Primary Online Voting

1. Eligibility. Only pupils with a valid admission number approved by the admin may vote. One admission, one vote, no transfers.

2. One ballot. Submitting is final. You cannot change, withdraw or re-vote. Double voting attempts are blocked and logged.

3. Your PIN. Keep it private. Anyone with your admission + PIN can vote as you. The school never asks for your PIN outside this site.

4. Fair use. Do not impersonate, coerce others, or interfere with the service. Fraud reports are reviewed; abuse may lead to disciplinary action.

5. Availability. Free-tier hosting may cold-start (a few seconds) and resets the temporary database on redeploys — seed data is restored automatically for demos.

6. Changes. The admin may reset the election (clearing votes/HasVoted) when authorised. Terms may be updated; continued use means acceptance.

Privacy Policy

Last updated: 28 September 2026 — Kericho Primary Online Voting

What we collect: Admission number, name, class, and a hashed PIN (never plain text). Votes are counted per candidate; the system links a voter to “has voted” but does not expose individual choices to other pupils.

What we store: SQLite file on the server. On the free host the file is ephemeral and re-seeded on restart. Fraud and contact messages are stored for admin review.

Who sees it: Only the authenticated admin (username/password, token-gated API) can see turnout, tallies, registrations, fraud and contact messages.

Security: PINs are SHA-256 hashed. Admin routes require x-admin-token. Inputs are validated and transaction-wrapped. No third-party trackers.

Your rights: Ask the admin to correct your registration or remove a fraud/contact message you submitted. Votes cannot be undone after submission.

Contact: Use the Contact page or speak to the supervising teacher (Grofry Rotich).

Kericho Primary — Online Voting: How the whole thing works

For the admin and supervising teacher. Print this page with the “Print Guide” button.

Stack: Node 24 built-in http + node:sqlite (no npm), single static client, SQLite file voting.db (ephemeral on Render free tier, auto-seeded). Admin auth via x-admin-token.

1. Who can vote

Any pupil with an approved admission number + PIN. New pupils register on the site; admin approves/rejects in Admin → Registrations. Seed demo voters: KP001–KP010 (PIN 1234).

2. The ballot

Five positions, two candidates each: Head Boy, Head Girl, Assistant Head Boy, Assistant Head Girl, Games Captain. Exactly one choice per position. Submit is validated server-side (missing, invalid ID, or cross-position candidate → rejected; HasVoted blocks a second submit forever).

3. Registration → approval flow

  1. Pupil submits POST /api/register → row in voter_registrations as pending.
  2. Admin lists GET /api/admin/registrations (pending first), then POST /approve/:id (inserts into voters + approved) or POST /reject/:id (rejected → pupil can re-apply).
  3. Approved pupil logs in POST /api/login → receives candidate list; then POST /api/vote.

4. Results & turnout

GET /api/results (admin only) returns byPosition[{candidateId,name,class,votes,percent}] plus turnout. Percent per position = votes / total-votes-in-position. Admin dashboard shows KPIs and bars.

5. Safety controls

  • PINs stored as SHA-256 hex, never plaintext.
  • POST /api/reset (admin only) clears votes and HasVoted in a transaction.
  • Fraud reports (POST /api/fraud public) and contact messages (POST /api/contact public) visible only to admin.
  • Server binds 0.0.0.0:${PORT} (Render injects PORT), NODE_VERSION=24 on Render.

6. Running locally

node server.js → http://localhost:3000. Tests: BASE_URL=http://localhost:3000 node test/smoke.mjs (or against https://kericho-voting.onrender.com).

7. Deploy & CI

GitHub marvel-254/kericho-voting main → Render service kericho-voting (Oregon, free, autoDeploy: yes, render.yaml). CI: .github/workflows/ci.yml runs node --check + smoke on push/PR.
